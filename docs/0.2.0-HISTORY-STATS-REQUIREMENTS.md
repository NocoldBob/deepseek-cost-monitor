## 1. 背景与目标

### 1.1 背景

0.1.1 已经能读取本机 Claude Code 会话日志，按 DeepSeek 官方价目估算**今天**的消费，并在侧边栏和状态栏展示。

但用户实际使用时，通常关心的是更长周期的花费：

- 昨天、上周、上月花了多少
- 这个月和上个月相比是涨还是跌
- 哪些天消费异常
- 本季度、今年累计花了多少

当前实现每次启动都会扫描 `~/.claude/projects` 下的历史 JSONL，原始数据其实已经存在，但生成快照时只保留北京时间“今天”的记录，历史数据没有被聚合、持久化或展示。

### 1.2 目标

把插件从“今日计数器”升级为“本地记账鲸鱼”：

1. 建立**每日账本**，持久化保存每日消费聚合数据。
2. 支持从日志回溯历史（**回溯上限受 Claude Code 的 `cleanupPeriodDays` 约束，默认约 30 天**，见 §4.10）；安装后即使日志被清理，已入账本的数据仍保留且不倒退；冷启动先读账本秒开，再后台扫描校正。
3. 提供历史统计界面：日、周、月、季、年视图。
4. 提供消费波动图和日历热力图。
5. 保持现有隐私边界：只读本地记录，不联网、不需要 API Key、不上传数据。
6. 保持跨平台：Windows 10/11、Ubuntu 22.04/24.04、macOS，同一个 VSIX。

### 1.3 成功标准

- 用户打开历史页，可以看清最近 30 天的每日消费和波动。
- 用户切换周、月、季、年，查看对应周期的汇总和趋势。
- 重启 VS Code 后历史不丢失；Claude Code 日志被清理后，已记录的历史仍保留且不倒退。
- 删除本地 Claude Code 日志后，已记账的日期金额不变；界面上“无数据”与“零消费”可区分，不把缺失当成 0。
- 用户能知道回溯窗口受 Claude Code 保留期限制，以及如何延长它（FR-19 提示）。
- 冷启动时历史页不需要等待日志扫描即可显示内容（≤ 150 ms 出首屏）。
- 今日页与历史页中的“今天”金额始终一致。
- 今日页的行为与 0.1.1 保持一致，不因新增历史功能而退化。
- 不引入网络请求、遥测或新的运行时依赖。

## 3. 用户场景

### S1 每日查看

用户每天打开 VS Code，希望看到今天到目前为止花了多少，和昨天大致对比。

### S2 周度复盘

用户想知道本周一到今天累计消费、日均消费，以及哪几天偏高。

### S3 月度 / 季度 / 年度统计

用户想知道本月、本季度、今年累计消费，以及按模型拆分的占比。

### S4 异常排查

用户发现某天消费明显偏高，希望通过热力图或波动图定位到具体日期，再查看当天的请求数和 token 明细。

### S5 日志清理 / 重装

用户清理了 Claude Code 历史日志、或 Claude Code 按默认 30 天策略自动清理了日志，或重装了 VS Code。希望已记录的历史不丢失，并明确区分“账本记录”和“日志可回溯”的数据。

关键点：用户常以为“历史只有一个月”是插件的问题，实际是 Claude Code 的默认保留期。产品需要在首次运行就说清这一点（FR-19），并在界面区分“可复核”与“仅账本记录”的日期。

### S6 设置调整

用户切换币种（CNY/USD）、调整模型前缀、开关子代理统计、修改价目或节假日，希望历史统计按新口径重新展示。

## 4. 术语与统计口径

### 4.1 记账日

- 以北京时间（UTC+8）划分，00:00:00 至 23:59:59.999 为一个记账日。
- 日期键格式：`YYYY-MM-DD`，例如 `2026-11-24`。
- 不使用本地系统时区，避免跨时区设备导致口径不一致。

### 4.2 安装日

- 扩展 0.2.0 首次成功运行并写入账本的日期。
- 用于在历史页标记“账本开始记录”的日期，不代表历史数据从这一天才有。
- 如果日志中存在更早的记录，历史页仍可展示，安装日只做标记。

### 4.3 请求 / 消息

- 以 Claude Code 会话记录中的 `message.id` 作为去重键。
- 同一个 `message.id` 的流式快照只计一次。
- 请求数按去重后的 assistant 响应计数。

### 4.4 Token 口径

- 缓存未命中输入：`input_tokens`
- 缓存命中输入：`cache_read_input_tokens`
- 缓存写入：`cache_creation_input_tokens`
- 输出：`output_tokens`
- 展示合计：缓存未命中 + 缓存命中 + 输出（与 0.1.1 一致）
- 缓存写入 token 计入账本，但当前价目按 0 计费；保留字段以便未来价目调整。

### 4.5 高峰 / 低谷

**官方口径（DeepSeek API 定价页，2026-11-24 核对）**：

> Peak hours are 01:00 - 04:00 and 06:00 - 10:00 UTC, Monday through Friday, excluding Chinese public holidays. All other hours are off-peak, including weekends and Chinese public holidays in full.

换算为北京时间（UTC+8）：

- **高峰**：**周一至周五**的 09:00–12:00、14:00–18:00。（两段窗口在 UTC 与北京时间属同一日历日，所以“星期几”的判定两边一致，不会出现跨日偏移。）
- **低谷**：其余全部时间，包括
  - 周六、周日**整天**——不区分该日是否为调休上班日；
  - 中国法定节假日**整天**（含落在工作日的假日）。
- 低谷价 = 高峰价的 50%。
- 每条请求按其自身时间戳判断峰谷，不按查看时的当前时段判断。

**易错点（务必按此实现，不要“优化”）**：

- **调休上班日（补班的周六/周日）仍按低谷计价。** 官方规则按日历星期“周一至周五”判定，并明确“周末整天属低谷”。因此 2026-02-14、2026-02-28、2026-05-09 这类补班日**不构成高峰**；`2026-10-10`（周六补班）同理。
- 反向也成立：落在工作日的法定假日（如 2026-02-16 周一）属低谷，已在 `holidays` 集合覆盖。
- 因此 `isPeak(tsMs, holidays)` **不需要新增“调休上班日”维度**。0.1.1 的现有实现（周末→低谷、`holidays`→低谷、其余按小时段判定）与官方口径一致，**0.2.0 不改变计价语义**。
- 法定节假日集合取国务院办公厅当年度《放假安排》中“放假”的日期（`isOffDay === true`），数据来源与更新流程见 §8.6。

> `nextBoundaryMs` 的边界时刻集合（0/9/12/14/18 点）与上述北京时间窗口一致，不需调整。

### 4.6 金额

- 金额是估算值，不是 DeepSeek 官方账单。
- 使用 DeepSeek 官方公开价目，支持 CNY / USD。
- 不做汇率换算；CNY 和 USD 各自按对应价目计算。
- 未知 DeepSeek 模型按 `deepseek-flash` 价估算并提示。
- 金额展示精度与 0.1.1 一致；详细值可在 tooltip 中查看。

### 4.7 周期定义

| 粒度 | 定义 | 键示例 |
|---|---|---|
| 日 | 北京时间自然日 | `2026-11-24` |
| 周 | 周一 00:00 至周日 23:59:59.999，周一为一周起点 | `2026-W48` |
| 月 | 北京时间自然月 | `2026-11` |
| 季 | Q1 1–3 月、Q2 4–6 月、Q3 7–9 月、Q4 10–12 月 | `2026-Q4` |
| 年 | 北京时间自然年 | `2026` |

> - 周使用“周一起始”的日历周，键中的年份为 **ISO 周年份**（例如 2027-01-01 属于 `2026-W53`），避免跨年周归属歧义。开发阶段需要补充跨年周边界测试。
> - 上述所有周期键都是**查询层的派生结果**，账本只存“日”，不存周/月/季/年聚合，避免出现两套互相矛盾的数据源。
> - 范围边界落在周期中间时，该周期为**不完整周期**，展示时必须标记（见 FR-10）。

### 4.8 数据来源

- 主数据源：`~/.claude/projects/**/*.jsonl` 中 `type === "assistant"` 的记录。
- 用户可通过 `deepseekCostMonitor.projectsPath` 指定其他目录。
- 账本是派生数据，用于持久化和快速查询；日志仍是原始数据源。
- 日志的**存在期由 Claude Code 控制**：`cleanupPeriodDays`（默认 30 天）会静默删除过期会话文件。因此真实可回溯范围 = 当前仍存在的日志，而非“全部历史”。账本的作用就是把这份数据从“30 天”延长到“装了插件之后的长期”，但无法覆盖从未被扫描到的部分（§4.10）。

### 4.9 今日页与历史页的数据来源（重要口径）

两个页面读取的数据源不同，必须显式约定，否则“历史页里今天这一格”会和“今日页”对不上：

| 视图 | 数据来源 | 说明 |
|---|---|---|
| 今日页（含按会话、按项目） | 内存实时快照 | 只有实时快照含 `sessionId`/`cwd`；账本按隐私要求不保存这两项 |
| 状态栏 | 内存实时快照 | 与今日页同源，始终一致 |
| 历史页 | 账本 | 关闭 VS Code 后仍可展示 |
| 历史页中“今天”这一格/这一行 | **实时快照覆盖账本值** | 账本对当天存在最长一个刷新间隔（默认 30s）的滞后 |

约定：

- 历史查询在聚合账本后，若所选范围包含北京时间今天，且当前窗口已有实时快照，则用实时快照的今日聚合**替换**账本中今天的桶。
- 替换按桶取 `max`，保证只增不减（实时值通常不小于账本值，日志被删时也不会倒退）。
- 因此：**历史页今天的金额 = 今日页金额 = 状态栏金额**，这是可验收的硬约束（见 FR-04）。
- 冷启动尚未拿到实时快照时，历史页的今天先用账本值展示并标记“校正中”，不显示为空。

### 4.10 数据完整性边界（日志被删除后数字还对不对）

**前提事实（必须写进 README 与 MARKETPLACE）**：Claude Code 自身会按 `cleanupPeriodDays` 静默删除 `~/.claude/projects` 下的会话记录，**默认 30 天**，删除时不提示（`claude --resume` 找不到会话往往就是这件事）。所以“用户删除本地对话历史”不是边缘情况，而是**默认配置下必然发生的事件**，它直接决定本插件的回溯窗口上限。

**因此账本必须被正确定位：它是捕获器，不是备份器。** 它只能保留“扩展运行期间扫描到过”的数据，不能恢复自己从未见过的东西。据此，日志删除后的正确性只有四种情况：

| 情况 | 该日 token / 金额 | 说明 |
|---|---|---|
| A. 该日**已入账本**，之后日志被删或截断 | ✅ **正确，且不倒退** | 账本已保存该日 token 桶，删日志不影响；重算值变小被 max 合并忽略（§6.4）。峰谷分桶冻结并标 `bucketingStale` |
| B. 该日在**入账本之前**日志就被删 | ❌ **永久缺失，无法恢复** | 例如装插件前已被 30 天清理；或某段时间只在终端跑 Claude Code、从未打开 VS Code。属物理限制，明确不做“猜数”补偿 |
| C. 删除的是**今天**的日志 | ⚠️ **需专门约定**，见下 | 实时值变小，但账本今日值更大；必须保证页面不倒退且三处一致 |
| D. 用户主动执行“从日志重建账本”（FR-16） | ❌ 已删日志对应的数据被清除 | 该命令是 replace 语义，属预期行为，确认文案须写明 |

**情况 C 的专门约定（rev.4 修补的漏洞）**：今日页走实时快照，日志一删金额立刻掉；而历史页“今天”按 §4.9 取 `max(账本, 实时)` 不会掉。两者会不一致，直接违反 FR-04 的“今日页=历史页今天=状态栏”硬约束。修补如下：

- 今日页与状态栏的**今日合计金额**同样取 `max(实时快照, 账本今日值)`；账本值更大时以账本值展示。
- 同时今天在今日页顶部显示一行提示：“本地日志少于已记录数据（可能被清理），当前展示账本记录值”。
- **“按模型”可用账本兜底**（账本按模型分桶），必须一并兜底，否则今日页各分区自相矛盾。
- **“按会话 / 按项目”无法兜底**（账本按隐私要求不存 `sessionId` / `cwd`），该分区显示“部分记录已不在本地日志中，明细合计可能小于总计”。这是有意为之的一致性妥协，不伪造维度。

**“还对不对”的诚实结论**：

- 对**进过账本**的日期：金额正确。token 是原始事实，价目变更仍可重算；删日志不会让已记录的数字变错，只是无法再复核与重划峰谷。
- 对**从未进过账本**的日期：不是“算错”，而是“没有数据”。界面必须区分这两件事——**空白天 ≠ 零消费**（见 FR-12 与 §7.2）。
- 因此账本中每天多存一个 `lastRecomputedAt`：该日最近一次从日志成功重算的时间。有值 = 可复核；无值 = 只剩账本快照，与 `bucketingStale`（口径是否过期）是两个独立概念，不可互相替代。

**由此产生的产品义务**：安装与首次运行、以及诊断信息里，必须如实告知回溯窗口受 `cleanupPeriodDays` 约束，并给出可操作建议（FR-19）。

### FR-01 每日账本持久化

**描述**

- 扩展应把每日聚合结果持久化到 VS Code 扩展的 `context.globalStorageUri` 下。
- 账本按北京时间日期键保存；每天每个模型、每种峰谷状态、主请求/子代理分别保存聚合数据。
- 账本只在本地保存，不同步、不上传。

**验收标准**

- 首次运行 0.2.0 后，`globalStorageUri` 下存在账本文件。
- 关闭并重新打开 VS Code 后，历史数据仍在。
- 删除全部 Claude Code 日志后重新打开，已写入账本的日期仍可展示。
- 账本文件不包含聊天内容、会话 ID、cwd 或文件路径。

### FR-02 历史回溯与账本合并

**描述**

- 0.2.0 首次运行时应从现有日志回溯历史，生成账本。
- 日志中有、账本中没有的日期，应被补入账本。
- 重复扫描同一批日志不得重复计费；账本更新必须幂等。
- 账本中存在、日志中已不存在的日期，应保留账本数据。
- 合并采用 **按桶单调取大（max merge）**，不采用“累加”也不采用“直接覆盖”；完整规则见 §6.4。
- 账本在正常情况下**只增不减**：删除或截断日志不会让已记录的数字变小。
- 若用户确实需要按当前日志重新计算（例如纠正错误），使用显式的“从日志重建账本”命令（FR-16 一并实现），重建是该语义的唯一入口。
- **能力边界（不可承诺）**：账本只能保留“扩展运行期间扫描到过”的数据。某天的日志在首次被扫描之前就被删除（含 Claude Code 默认 30 天自动清理），该天数据永久缺失，不做猜测补偿。完整判定见 §4.10。

**验收标准**

- 首次运行后，历史页能展示安装日之前日志中存在的日期。
- 连续刷新、重启多次，金额和请求数不重复累加（连刷 20 次，数值保持不变）。
- 删除某个日志文件后，已记录日期的数据不消失，也不变小。
- 把某天的日志截断为一半后刷新，该天数值保持不变（不倒退）。
- 日志已被删除的日期，历史页标注“仅账本记录”（`lastRecomputedAt` 停止更新），与“日志可复核”的日期在视觉与 tooltip 上可区分。
- 日志在首次被扫描前即被删除的日期，显示为“无数据”而不是“¥0.00”，两者不得混淆（§4.10、FR-12）。
- 新增日志后，下一次刷新能补入新数据（数值按 max 增长）。
- 同一份日志被两个窗口各扫一遍，账本数值不翻倍。

### FR-12 空状态、错误状态与损坏恢复

**描述**

- 无日志目录：提示目录不存在，并提供设置入口或诊断命令提示。
- 有日志但无消费数据：显示“暂无数据”，不报错。
- 账本损坏、格式不兼容或写入失败：保留原文件备份，尝试从日志重建，并在界面/输出面板提示。
- 账本 `schemaVersion` 高于当前插件支持：**只读降级**，历史照常展示，禁止写入，提示“请升级插件”。
- 部分日志读取失败：继续展示可用数据，并提示读取失败文件数。
- **“无数据”与“零消费”必须区分**：某日既不在账本也无日志记录 → 明细与热力图显示“无记录”空态，**不显示 `¥0.00`**；某日有请求但金额恰为 0（例如全部命中缓存）→ 正常显示 `¥0.00`。两者样式不同，避免用户把“没数据”误读成“没花钱”。
- **“仅账本记录”的日期**（`lastRecomputedAt` 缺失，或早于该日日志最后一次存在的时间）：正常展示金额，tooltip 注明“该日日志已不在本地，无法复核；峰谷口径可能已过期”。
- `bucketingStale` 的日期：正常展示，但在 detail/tooltip 与诊断信息中提示“该日峰谷口径已过期，日志缺失无法重算”。

**验收标准**

- 删除/重命名 `projectsPath` 后，界面显示明确错误，不崩溃。
- 人为破坏账本 JSON 后，扩展能备份并重建，或至少给出可操作的错误提示。
- 写入失败时旧账本保持可读，不产生空文件。
- 高版本账本被打开后，扩展不写盘，历史可读，提示可操作。
- 日志文件权限错误时，其他文件仍能统计。
- 无记录的日期显示空态而非 `¥0.00`；删掉某天日志后，该日仍显示原金额并标注“仅账本记录”。
- 错误信息不包含聊天内容或敏感路径以外的隐私数据。

### FR-13 设置实时生效

**描述**

不同设置影响的层级不同，必须分开说明，避免“改了节假日要不要重算历史”这类争议：

| 设置 | 生效层级 | 是否影响历史 |
|---|---|---|
| `currency` | 仅计算与展示 | 是，历史金额立即按新币种重算（token 不变） |
| `rateOverrides` | 仅计算 | 是，历史金额按新价目重算 |
| `modelPrefixes` | 仅查询过滤 | 是，历史按新前缀重新过滤（账本保留全部模型） |
| `includeSubagents` | 仅查询过滤 | 是，历史按主/子桶重新过滤（账本分桶已含主/子） |
| `holidays` | **重算分桶** | 是，但仅限日志仍存在的日期；日志已删除的日期无法追溯（见下） |
| `projectsPath` | 重扫 + 合并 | 新目录数据并入，旧目录已记录日期不丢失（同一天同桶取大，不叠加） |
| `refreshIntervalSeconds` | 仅调度 | 否 |
| `showStatusBar` | 仅 UI | 否 |

关于节假日变更的追溯口径（替换原 Q3）：

- 每次写入账本都是**从日志全量重算日聚合**（§6.4），因此只要某天的日志还在，`holidays` 变更后该天就会按新表重新划分高峰/低谷，属于**自动追溯**。
- 注意：调休上班日不参与峰谷判定（§4.5），所以补充调休数据不会改变任何历史金额；`holidays` 变更只影响“落在工作日但被列为放假”的日期。
- 只有日志已被清理的日期无法追溯，保留原分桶，并在该日标记 `bucketingStale: true`；诊断信息与历史页 tooltip 提示“该日峰谷口径已过期，日志缺失无法重算”。
- 这样既不需要在账本里保存小时级数据（原 Q3 选项 B 的复杂度），又能在日志可得时给出最准确的历史。

**验收标准**

- 切换 CNY/USD 后今日与历史金额同时更新。
- 关闭子代理统计后，历史金额和请求数按去除子代理后的口径展示。
- 修改 `rateOverrides` 后，历史金额按新价目重算，并在界面注明“历史金额按当前价目重算”。
- 修改 `holidays` 后，日志仍在的日期的峰谷分桶按新表重算；人为删除某天日志后再改表，该天数值不变并出现 `bucketingStale` 提示。
- 修改日志目录后，账本合并新目录数据，不丢失旧账本日期；同一天在两目录都存在时取逐桶较大值，不做加和。

### FR-14 多窗口账本一致性

**描述**

- 用户可能同时打开多个 VS Code 窗口，每个窗口都会激活扩展并可能写入同一个账本。
- 多窗口同时运行时，账本不得损坏、不得重复计数、不得出现半写入文件。
- 采用 **跨进程写锁 + 写前重新读取 + 逐桶 max 合并 + 原子替换**；只靠“后写者胜”会导致旧内存覆盖另一窗口新写入的日期，见 §6.6。
- 影响峰谷分桶的设置（`holidays`）改为 **machine 作用域**，保证同一台机器上所有窗口的分桶口径一致；账本记录 `bucketSignature` 用于校验，防止不同口径的数据被合并成双计。

**验收标准**

- 两个窗口同时刷新时，账本仍可被解析，不出现半截 JSON。
- 同一批日志不会被重复累加；两窗口各刷 20 次后，账本数值与单窗口一致。
- 关闭其中一个窗口不影响另一个窗口的历史展示。
- 人为让两个窗口持有不同的 `bucketSignature` 时，账本不会把同一批请求同时计入高峰和低谷（总 token 不膨胀）。
- 写入失败（文件被占用、磁盘只读）时，旧账本保持可读，错误只出现在输出面板，不弹阻塞式对话框。

### FR-15 诊断信息包含账本状态

**描述**

“DeepSeek: 输出诊断与自检信息”命令增加账本信息：

- 账本文件路径
- schema 版本
- 已记录天数、最早/最晚日期
- 安装日
- 最近写入时间、最近一次“从日志重建”时间
- 读取/写入错误、写入重试失败次数
- 账本大小
- `bucketSignature`（峰谷分桶口径签名）与 `bucketingStale` 的日期数量
- **数据可信度**：`lastRecomputedAt` 最近更新的日期、仅剩账本快照的日期数量
- **回溯窗口**：日志实际最早日期、账本最早日期、两者差值（说明有多少历史未被捕获），以及检出的 `cleanupPeriodDays`（FR-19，检出不到时标注“未检出”并说明不影响统计）

**验收标准**

- 诊断输出包含上述字段。
- 不输出聊天内容、会话 ID 或 cwd。
- 能用于排查账本损坏和重复计数问题。

### FR-16 账本维护命令（P1，rev.2 由 P2 上调）

**描述**

因为合并采用“只增不减”（§6.4），必须提供一个“让数字变小”的显式入口，否则一次错误估算会永久留在账本里。提供两个命令，均不清除 Claude Code 原始日志：

1. **DeepSeek: 从日志重建账本**（主入口）
   - 清空当前账本的日聚合，按当前日志全量重算并写入（使用当前 `holidays`，并写入新的 `bucketSignature`）。
   - 保留 `installDate`、`schemaVersion`；`firstRecordDate`/`lastRecordDate` 按重算结果更新。
   - 结果会**替换**而非合并，因此金额可能变小，这是该命令的预期语义。
   - 执行后写入 `lastRebuildAt`，诊断信息可见。
2. **DeepSeek: 清除历史账本**（隐私清理用）
   - 直接删除账本文件与备份文件。
   - 本次会话暂停自动写入，避免下一次 30 秒刷新立即把日志重新扫回；重新加载 VS Code 后会从日志重建。
   - 今日数据仍可由日志实时统计（今日页不依赖账本）。

**验收标准**

- 两个命令执行前均有明确确认提示，且提示文案说明“重建会让历史金额按当前日志重算，可能变小”。
- 重建后历史页数值与“把账本删掉再冷启动全量扫描”的结果一致。
- 清除后历史页为空，今日页与状态栏正常。
- 两者都不修改 `~/.claude/projects` 下的任何文件。
- 重建过程中若扫描失败，账本保持执行前的样子（不做半途替换）。

### FR-17 数据导出（P2，后续候选）

**描述**

支持导出 CSV / JSON，字段包含日期、模型、请求数、token、金额。本期不做。

### FR-18 冷启动快速路径（P0）

**描述**

账本存在的主要收益之一是“不必等扫描”。0.1.1 每次启动都要全量扫一遍日志才能出数，账本必须改变这一点，否则只是一个更大的缓存文件。

激活顺序（异步，不阻塞 UI）：

1. 读取账本，校验 `schemaVersion` 与结构；失败则跳过并走 0.1.1 路径（见 FR-12 恢复）。
2. 立即用账本渲染历史页，标记 `stale: true`，页面顶部显示轻量提示“正在校验历史数据…”。
3. 今日页允许用账本中“今天”的桶预填金额 / 请求数 / token / 按模型；`按会话`与“更新时刻”显示骨架占位。
4. 同时启动扫描（首次为全量），首份快照产出后发布，替换 `stale` 数据并撤掉提示。
5. 扫描过程中若账本已有内容，不得出现“空状态”闪烁。

其它约定：

- 账本缺失或损坏时，行为退化为 0.1.1：等待扫描完成后出数，不报错、不阻塞。账本 `schemaVersion` 更高但结构可解析时，按 FR-12 只读展示（可出首屏，但不写盘）。
- 冷启动期间历史页可交互（切换范围/粒度），但操作基于账本数据；扫描完成后自动按最新数据重绘，不重置用户已选的范围与粒度。
- 写账本时机为“首轮扫描完成”与“数据有变化时”，不做无变化重写（与 §9.1 一致）。

**验收标准**

- 已有账本时，冷启动历史页首屏在 150 ms 量级出现内容，且不等待日志扫描完成（用 > 100 MB 日志目录验证）。
- 首屏出现后，扫描完成时数据被校正，页面不闪白、不回到空状态。
- 今日页冷启动时先显示账本预填金额，扫描完成后金额、请求数、按会话分区补齐。
- 删除账本后冷启动，行为与 0.1.1 一致（等待扫描），无错误提示。
- 账本损坏时冷启动不崩溃，按 FR-12 备份并重建。

### FR-19 日志保留期检测与回溯窗口告知（P1，rev.4 新增）

**描述**

账本的回溯上限被 Claude Code 的 `cleanupPeriodDays`（默认 30 天）硬性约束，用户不知道这一点就会以为“历史只有一个月是插件的问题”。因此：

- **只读**探测 `~/.claude/settings.json` 中的 `cleanupPeriodDays`；**严禁写入、创建或修改该文件**，也严禁修改用户任何 Claude Code 配置。
- 检出值仅用于提示，**不作为任何计算依据**（企业 `managed-settings` 可能覆盖它，本地检出值未必是实际生效值）。
- 首次运行时在历史页显示一次性可关闭提示条：
  > Claude Code 默认在 30 天后删除本地会话记录（`cleanupPeriodDays`），可回溯的历史上限受此限制；已记入账本的数据不受影响。如需长期回溯，可在 `~/.claude/settings.json` 中调大该值（例如 `3650`）。
- 诊断信息中增加一行“日志保留期（检出值）/ 账本覆盖天数 / 最早可回溯日期”，用于解释“为什么更早的日期是空的”。
- 当账本最早日期晚于日志最早日期（说明有历史未被捕获），诊断中提示可尝试“从日志重建账本”补齐可回溯部分。

**验收标准**

- 全程只读：执行后 `~/.claude/settings.json` 的 mtime 与内容均不变；文件不存在时**不创建**。
- `settings.json` 不存在、JSON 解析失败或权限不足时静默跳过提示，不报错、不影响统计与历史展示。
- 该设置变化不改变任何金额、分桶或账本内容。
- 提示条可关闭，关闭后不再重复弹出（状态存 `globalState`）。
- 在任何平台（含 `CLAUDE_CONFIG_DIR` 自定义路径）都不因读不到配置而阻塞主流程。

## 6. 数据与存储要求

> 本节描述数据行为要求和建议结构，具体实现可在技术设计中调整，但不能违反隐私、幂等和一致性要求。

### 6.1 存储位置

- 使用 `context.globalStorageUri` 下的扩展私有目录。
- 不写入用户项目目录、不写入 Claude Code 日志目录。
- 账本按 VS Code 用户配置（Profile）隔离；不同 Profile 不共享历史。

### 6.2 建议文件

- `history-ledger.json`：每日聚合账本。
- `history-ledger.backup.json`：上一次成功写入的账本副本，用于损坏恢复（写主文件前先转存）。
- `history-ledger.json.tmp.<pid>`：原子替换用的临时文件，rename 成功后即不存在；进程异常退出遗留的 `*.tmp.*` 可在启动时安全清理。
- **不使用锁文件**：并发控制改用“后写者胜 + 原子替换”，理由见 §6.6。锁文件在 Windows 上既不可靠（rename 被占用即失败）又会引入超时/stale 死锁面，收益不抵成本。

### 6.3 建议 schema（v1）

```json
{
  "schemaVersion": 1,
  "installDate": "2026-11-24",
  "firstRecordDate": "2026-09-01",
  "lastRecordDate": "2026-11-24",
  "updatedAt": "2026-11-24T08:00:00.000Z",
  "lastScanAt": 1795524646192,
  "lastRebuildAt": null,
  "bucketSignature": "9f2c1ab34de5",
  "days": {
    "2026-11-24": {
      "lastRecomputedAt": 1795524646192,
      "bucketingStale": false,
      "models": {
        "deepseek-flash": {
          "main": {
            "peak": {
              "requests": 1,
              "cacheMiss": 1200,
              "cacheHit": 3400,
              "cacheCreation": 0,
              "output": 800
            },
            "offpeak": {
              "requests": 0,
              "cacheMiss": 0,
              "cacheHit": 0,
              "cacheCreation": 0,
              "output": 0
            }
          },
          "subagent": {
            "peak": { "requests": 0, "cacheMiss": 0, "cacheHit": 0, "cacheCreation": 0, "output": 0 },
            "offpeak": { "requests": 0, "cacheMiss": 0, "cacheHit": 0, "cacheCreation": 0, "output": 0 }
          }
        }
      }
    }
  }
}
```

说明：

- 按日、按模型、按主请求/子代理、按高峰/低谷分桶。
- 金额不写入账本，展示时按当前价目和币种计算（见 §8.1）。
- 账本不保存会话 ID、cwd、文件路径、聊天内容或原始 JSONL。
- 模型名只保存规范化后的名称。
- `bucketSignature`：对“排序后的 `holidays` + 固定时区 `+08:00`”做哈希得到的短串，用于判定分桶口径是否变化（§6.4 第 3 条）。排序后哈希保证表项顺序不影响签名。
- `bucketingStale`：仅在该日峰谷口径与当前口径不一致且日志已缺失时置 `true`，默认 `false` 可省略。用于界面提示“该日峰谷口径已过期”。
- `lastScanAt`：账本最近一次扫描的时间戳（epoch 毫秒）。每次合并都会在内存中推进；数据或“可复核/仅账本”状态发生变化时落盘。
- `lastRecomputedAt`：该日最近一次**出现在扫描结果中**的时间戳，**epoch 毫秒数值**（不是 ISO 字符串；`updatedAt` / `lastRebuildAt` 仍用 ISO 字符串便于人读）。判定“仅账本”时比较 `lastRecomputedAt < lastScanAt`：本轮扫描没有看到这一天。它与 `bucketingStale` 是两个独立维度：前者回答“还能不能拿日志核对”，后者回答“峰谷口径还是不是最新的”。
- `lastRebuildAt`：最近一次“从日志重建账本”（FR-16）的时间，仅在重建时写入。
- `schemaVersion` 仍为 `1`：0.1.1 没有账本，0.2.0 是账本的第一个版本，rev.2 的字段调整发生在文档阶段，不产生迁移。
- 单条请求级明细不落盘；账本是聚合数据，无法还原到单请求。

### 6.4 聚合与合并规则

**（1）重算单位与成本**

- 内存中维护 `dayAgg`：日 × 模型 × 主/子 × 高峰/低谷 × 字段 的聚合表。
- 首次全量扫描时构建 `dayAgg`；之后每批新增记录只做**增量累加**，刷新成本与 0.1.1 相同（O(新增记录)），不随历史长度增长。
- `holidays` 变更时，用内存中已有的记录重建一次 `dayAgg`（O(全量记录)，不重读磁盘）。

> **实现注记（rev.5，M1 落地时确认）**：v1 采用「**全量重算 + 版本号短路**」而不是增量累加。
> 原因：`UsageStore` 在流式回复时会把同一 `message.id` 替换成输出更大的快照（`isBetterSnapshot`），
> 增量累加会把这些修正重复计入；要做正确的增量，必须先做“减旧值再加新值”，复杂度与出错面都不划算。
> 全量重算在这台机器上实测 8085 条记录 **8 ms**，10 万条量级仍在几十毫秒内，且随记录数线性、与历史长度无关。
> 短路方式：`UsageStore` 无新增/无替换时跳过重算。若未来日志量级增长到需要真正的增量，
> 应让 `UsageStore` 暴露“本批新增/被替换的记录”，再按 §6.4（2）的 max 语义做差量更新。

**（2）合并算法：逐桶逐字段单调取大（max merge）**

对每个 `日 × 模型 × 主/子 × 峰谷 × 字段`，写入值为：

```text
写入值 = max(账本原值, dayAgg 重算值)
```

覆盖的字段：`requests`、`cacheMiss`、`cacheHit`、`cacheCreation`、`output`。

为什么是 max，而不是其它两种直觉写法：

| 方案 | 问题 |
|---|---|
| 用重算值覆盖 | 日志被删除或截断时数字倒退，直接违反 FR-02 |
| 与账本相加 | 重复扫描同一批日志会翻倍，违反幂等 |
| **逐桶取 max** | 幂等、只增不减；且正常增长时与“覆盖”等价，因为新值全面 ≥ 旧值 |

由于 token 与请求数在正常情况下不会合法变小（当天在进行中只增；历史日期已定型），取 max 不会吞掉真实数据。唯一需要“变小”的场景是纠错，由 FR-16 的“从日志重建账本”命令承担。

**（3）分桶口径变更时的例外（防双计）**

账本顶层保存 `bucketSignature`。写入前比较签名：

- **签名相同**：按第（2）条做 max 合并。
- **签名不同**：对本轮扫描到的所有日期，用 `dayAgg` **整日替换**（不做 max）；对本轮没有扫描到任何记录的日期（日志已删除），保留原值并置 `bucketingStale: true`。替换后更新 `bucketSignature`。

这一条不是可选项。若两个持有不同 `holidays` 表的写入方对同一天做 max，同一条请求会同时落在高峰桶和低谷桶，总 token 直接翻倍。整日替换 + 签名校验从根上消除这个可能。

**（4）日期集合的边界**

- `days` 的键 = 账本已有日期 ∪ `dayAgg` 有数据的日期。
- 账本中“日志已消失”的日期永不删除，这是账本存在的意义。
- `firstRecordDate` / `lastRecordDate` 随实际日期集合重算。

**（5）写入原子性**

1. 序列化 → 写入 `history-ledger.json.tmp.<pid>` → `fsync` → `rename` 覆盖正式文件。
2. `rename` 在 Windows 上可能因杀毒/索引占用返回 `EPERM`/`EBUSY`，需重试 3 次（间隔 50 ms / 150 ms / 400 ms）。
3. 三次失败则**放弃本轮写盘**：旧账本保持完好，错误写入输出面板，下次刷新自动重试。不得删除或清空旧账本。

**（6）无变化不写盘**

序列化结果的哈希与上次写入一致时跳过写盘。避免 30 秒定时刷新产生无意义的磁盘写入（§9.1）。

**（7）版本**

所有写入必须带 `schemaVersion`。读到更高版本的账本时按 §6.9 处理，不得凭旧结构覆盖。

### 6.5 安装日与首次记录日

- `installDate`：0.2.0 首次成功运行日期。
- `firstRecordDate`：账本中最早有数据的日期，可能早于 `installDate`。
- 如果账本被删除但 `globalState` 仍保留安装日，应优先保留原安装日；如无法恢复，则重置为当前日期并在诊断中提示。
- `installDate` 一经写入不再改变，“从日志重建账本”（FR-16）也必须保留它；只有“清除历史账本”会一并清除，重新记账时重新生成。
- `lastRecordDate` 与 `firstRecordDate` 都由第 6.4（4）条的日期集合推导，不单独维护。

### 6.6 并发与多窗口

**结论：写锁 + 写前重新读取 + 逐桶 max 合并 + 原子替换。**

- 仅靠“后写者胜”不够：后写者可能在加载后没有重新读取，用旧内存账本覆盖另一个窗口刚写入的日期（实测会丢整天数据）。因此写盘必须：
  1. 获取跨进程写锁（`history-ledger.lock`，`wx` 创建，stale 超时自动清理）；
  2. 重新读取磁盘账本；
  3. 把磁盘、内存、本轮扫描三份来源按口径合并；
  4. `tmp + rename` 原子替换；
  5. 释放锁。
- 拿不到锁时跳过本次写盘并记录错误，下次刷新重试；绝不阻塞今日页或损坏旧账本。
- 配合 §6.4 的逐桶 max 合并，同一批日志重复扫描不会重复计数；日志被删除后旧值保留。
- 分桶口径不同（`bucketSignature` 不同）时仍按整日替换处理，避免同一条请求同时落入高峰/低谷桶。

**必须一致的是“分桶口径”，不是“写入顺序”：**

- `deepseekCostMonitor.holidays` 建议由 `window` 改为 **`scope: "machine"`**。它是数据表而非个人偏好，同一台机器上所有窗口必须用同一张表；否则同一批请求会在不同窗口被分到不同峰谷桶。
- 即便如此，仍保留 `bucketSignature` 校验（§6.4（3）），作为跨版本、跨配置残留数据的兜底。
- 补充：`globalStorageUri` 按 VS Code Profile 隔离（§6.1），因此不同 Profile 之间不会互相写入账本；签名不一致只可能来自“同一 Profile 内配置被并发修改”或“插件版本不同”，两者都由整日替换保证结果正确（可能产生一到两次重算，但不会双计）。

**已知限制（写进文档，不试图解决）：**

- 两个窗口的 `projectsPath` 不同且扫描的目录互不包含时，同一天的合并结果是**逐桶取大而非并集求和**，会低估两目录合计。要正确合计，需把目录合并到同一路径，或执行“从日志重建账本”。这一取舍优先保证“不重复计数”，因为重复计数的错误更难被发现和理解。

### 6.7 数据保留

- 默认无限期保留每日聚合数据。
- 账本体积预计很小（每年约几百 KB 量级），不设置强制保留期。
- 后续可增加 `historyRetentionDays` 设置；本期不做。
- **原始日志的保留期不由本插件决定**：Claude Code 按 `cleanupPeriodDays`（默认 30 天，静默）删除 `~/.claude/projects` 下的会话文件。因此：
  - 首次安装时的可回溯范围 = 当前仍未被清理的日志，通常只有最近 30 天，而不是“历史全部”；
  - 账本的长期价值恰恰来自这一点：它把数据保留期从“Claude Code 的 30 天”延长到“用户保留插件的一天”；
  - 但扩展不运行期间产生的日志不会被捕获，这段数据一旦被清理即永久缺失（§4.10 情况 B）。
- 本插件**永不修改** `~/.claude/settings.json` 或任何 Claude Code 配置；只在 FR-19 中只读探测保留期并提示。

### 6.8 隐私

账本只允许保存：

- 日期
- 规范化模型名
- 请求数
- token 计数（含缓存写入）
- 高峰/低谷标记
- 主请求/子代理标记
- schema 版本、安装日、更新时间、`bucketSignature`、`lastRebuildAt`

禁止保存：

- 聊天内容、prompt、completion
- 会话 ID
- cwd、项目路径、文件路径
- API Key、令牌、环境变量
- 任何可识别用户身份的信息

### 6.9 数据迁移

- 0.1.1 没有账本；0.2.0 首次运行从日志重建，不涉及旧账本迁移。
- 未来 schema 升级需提供迁移函数；无法迁移时备份原文件并从日志重建。
- 读到 `schemaVersion` 高于当前插件支持的账本时：**只读模式**——可以读取展示，但禁止写入（避免用旧结构覆盖新数据），界面提示“账本由更新版本的插件写入，请升级插件”。

### 7.2 交互要求

- 切换标签页不重新激活扩展，不丢失状态。
- 日期范围和粒度变化后，汇总、图表、模型统计、明细表同步更新。
- 图表 tooltip 显示周期、金额、请求数、token；金额与币种一致。
- 热力图 tooltip 显示日期、金额、请求数、token。
- 所有金额和 token 使用与今日页一致的格式化规则；精确值放 tooltip。
- 加载中显示占位或骨架，不显示上一次范围的错误数据。
- 冷启动“校正中”状态用轻量行内提示表达（不使用模态框、不阻塞操作），扫描完成后自动消失。
- 明细表与热力图的 tooltip 需能在以下情况给出说明：周期不完整（`*`）、`bucketingStale`（“峰谷口径已过期”）、未知模型估算、价目覆盖。
- **数据可信度标注**：仅剩账本快照的日期（`lastRecomputedAt` 缺失或已过期）在明细行加轻量标记，tooltip 说明“该日日志已不在本地，无法复核”；无记录日期显示空态“无记录”，与 `¥0.00` 样式明确不同（§4.10、FR-12）。
- **今日页日志减少提示**：检测到实时值小于账本今日值时，页顶显示一行可关闭的说明，不弹窗、不阻塞；说明“按会话/按项目”明细可能小于合计。
- 侧边栏较窄时，图例、表格列可折叠或横向滚动，不能撑破布局。

### 7.3 视觉与主题

- 使用 VS Code 主题变量（`--vscode-*`），兼容浅色/深色/高对比度主题。
- 图表不使用远程字体、图片或脚本。
- 热力图颜色需要在浅色和深色主题下都可区分；建议使用主题强调色或中性色阶。
- 动画遵循 `prefers-reduced-motion`。
- 不使用会造成误导的 3D 图表或装饰性动画。

### 7.4 可访问性

- 图表提供文本摘要或可读的明细表，作为视觉信息的替代。
- 按钮、标签页可通过键盘访问。
- 颜色不是唯一的信息载体；热力图需有 tooltip 和数值表。
- 字号、对比度遵循 VS Code 默认主题。

## 8. 计价规则

### 8.1 历史金额口径

- 账本保存 token 与请求聚合，**不保存最终金额**（已定为决策，见 §13）。
- 历史金额在展示时按**当前价目表**和**当前币种**计算。
- 价目调整、覆盖价目修改后，历史金额会变化；历史页需注明“历史金额按当前价目估算”，README 也需说明“同一份历史在插件升级后可能显示不同金额”。
- 之所以不冻结金额：DeepSeek 官方调价后，冻结的旧金额会与用户实际账单脱节；而 token 是客观事实，永远可重算。

### 8.2 高峰/低谷与节假日

- 每条请求在聚合时按当时时间戳判断高峰/低谷，并计入对应桶。判定规则以 §4.5 的官方口径为准（周一至周五的北京时间 09:00–12:00、14:00–18:00 为高峰；周末与法定节假日整天为低谷）。
- 账本按“高峰/低谷”分桶保存，以便在价目变化时重算金额，而不必保留小时级数据。
- **节假日变更的追溯口径（已定）**：因为每次写入都是从日志全量重算（§6.4），所以只要日志还在，改表后相关日期会自动按新表重新划分峰谷；日志已删除的日期无法追溯，标记 `bucketingStale` 并在界面提示。这条同时替代了原 Q3 的“A 不追溯 / B 保存小时级”二选一——两者都不需要了。
- **节假日表必须覆盖可回溯年份**：内置表至少覆盖 2024–2027（按国务院办公厅放假通知核对，来源与更新流程见 §8.6）。表内缺失的年份退化为保守规则（仅按“日历周末 = 低谷”计算，不识别法定假日），并在历史页与诊断信息中提示“YYYY 年节假日表缺失，该年金额可能偏高（落在工作日的法定假日被当成工作日计算）”。不允许静默按此规则计算而不提示。
- 用户可通过 `deepseekCostMonitor.holidays` 覆盖内置表，语义为**整体替换**（设置了数组即完全替代内置表，不做合并）。这是给“国务院临时调整放假安排”或“内置表尚未更新”留的应急口子。

### 8.3 币种

- `currency` 切换只影响展示和计算，不修改账本 token 数据。
- CNY/USD 各自使用对应价目，不做汇率换算。

### 8.4 未知模型与非 DeepSeek 模型

- 默认只展示匹配 `modelPrefixes` 的模型。
- 账本**保存所有模型**的聚合数据（已定，见 §13），以便修改 `modelPrefixes` 后历史仍能重新过滤。代价是账本略大，按每年几百 KB 量级可接受。
- 未知 DeepSeek 模型按 Flash 价估算并提示。
- 非 DeepSeek 模型不参与默认统计；若用户把前缀改为其他模型，按现有价目逻辑处理（未知价目按 Flash 估算并提示）。

### 8.5 子代理

- 账本按主请求/子代理分桶。
- `includeSubagents` 变化时在查询时过滤，不修改账本。
- 默认为计入子代理（与 0.1.1 一致）。

### 8.6 节假日数据源与更新流程（离线，已选型）

**结论：采用 `NateScarlet/holiday-cn` 的 JSON 数据，构建期内置，运行时不联网。**

选型对比：

| 方案 | 形态 | 数据覆盖 | 许可证 | 运行时依赖 | 结论 |
|---|---|---|---|---|---|
| **holiday-cn**（NateScarlet） | 每年一个纯 JSON | 2007–2027（每日自动抓国务院公告） | MIT | 无（只内置数据文件） | **采用** |
| chinese-days（vsme） | TS 库 + JSON + iCal | 2004–2026 | MIT | 需装 npm 包 | 不采用（本项目只需一张日期表，引入库违反 §9.5） |
| chinese-calendar（LKI，Python） | Python 库 | 2004– | — | 不适用 | 不采用，仅作 holiday-cn 的上游数据参考 |

为什么是它：

- **纯数据**，没有代码、没有依赖树，符合“不引入新的运行时依赖”。
- 结构极简：`{ year, papers: [gov.cn 链接], days: [{ name, date, isOffDay }] }`。
- **`papers` 字段直接给出国务院公告链接**，可溯源、可审计，便于 CHANGELOG 记录依据。
- GitHub Action 每日抓取公告并自动发版，2027 年数据已于 2026-11-05 发布，跨年不会断档。
- 只取 `isOffDay === true` 的日期作为 `holidays` 集合。`isOffDay === false` 是调休上班日，**按 §4.5 的官方口径不参与计价，直接丢弃**。

落地方式：

- `tools/sync-holidays.mjs`（开发期脚本）：拉取 2024–2027 的年度 JSON，合并去重后生成 `src/holidays.data.js`（导出 `{ years: [...], byYear: { 2026: ['2026-01-01', ...] } }`），随 VSIX 打包。
- 内置 2024–2027 四年，未压缩体积约 6 KB（约 120 个日期），对 §9.6 的体积预算无压力。
- **运行时不发任何网络请求**：脚本只在开发机/CI 执行，不注册 `activationEvents`，扩展激活路径不包含这段代码。
- 许可证合规：MIT，需在 `ASSET-LICENSE.md` 增加条目并保留 `Copyright (c) 2019 NateScarlet` 与许可证全文引用（`resources/` 下的数据文件也要带上来源注释）。
- 校验：现有的 2026 内置表与 holiday-cn 的 2026 数据**逐条一致**（元旦 3 天、春节 2/15–2/23、清明 4/4–4/6、劳动 5/1–5/5、端午 6/19–6/21、中秋 9/25–9/27、国庆 10/1–10/7），因此 0.2.0 切换数据源**不会改变任何 2026 年的历史金额**。

已知数据陷阱（同步脚本需处理）：

- 该仓库按“国务院文件标题年份”归档，12 月的日期可能出现在次年的文件里 → 脚本合并多年度文件后按日期去重，**不按年份分桶存储**，因此不受影响。
- 其 README 说明“与周末连休的周末不是法定节假日，数据里不会包含”——对本项目无影响，周末本就是低谷。

年度维护：

- 每年 11 月国务院发布次年安排后，执行 `npm run sync:holidays`，把当年的 `papers` 链接写进 `CHANGELOG`，随下一个补丁版本发布。
- 用户未升级导致年份缺失时，按 §8.2 的保守规则计算并提示，不影响已有年份的数据。

## 9. 非功能需求

### 9.1 性能

- 首次全量扫描与账本构建不得阻塞 VS Code UI；继续使用异步分块扫描。
- **冷启动不等待扫描**（FR-18）：读账本 + 历史页首屏 ≤ 150 ms（1 年账本约 500 KB）。
- 历史查询（1 年日粒度、假设 10 个模型）应在 100 ms 量级完成。
- 刷新时的聚合成本为 O(新增记录)：`dayAgg` 增量累加，不做逐次全量重算；整体与 0.1.1 同量级。
- 账本写入应在 50 ms 量级完成；序列化结果无变化时跳过写盘，30 秒定时刷新不应产生磁盘写入。
- 100 MB 日志的首次扫描目标：不超过 5 秒（以开发机为准，允许合理浮动）。
- 图表渲染在侧边栏宽度下保持流畅，不因 365 个数据点卡顿。

### 9.2 跨平台

- Windows 10/11、Ubuntu 22.04/24.04、macOS。
- 使用 VS Code API 和 Node 标准库，不硬编码路径分隔符或用户目录。
- 同一个 VSIX 跨平台通用；CI 在三个 runner 上打包和跑场景测试。

### 9.3 可靠性与数据安全

- 账本写入原子化，崩溃或断电不得产生半写入 JSON。
- 启动时校验账本结构；损坏时备份并从日志重建。
- 多窗口并发采用“后写者胜 + 原子替换”，不得损坏账本或重复计数（§6.6）。
- 账本只能通过“只增不减”的合并规则或显式的重建命令改变，禁止任何隐式的数值回退。
- 不因历史功能引入网络请求、遥测或远程资源。
- 不读取或保存任何凭据、API Key、私钥。
- 只读原则：**不修改** Claude Code 的任何文件或配置（含 `~/.claude/settings.json`、日志目录）；唯一例外是用户显式触发的账本维护命令，且它们只操作扩展私有目录。
- 诚实呈现：不把“没有数据”显示成“消费为 0”，不把“仅账本快照”显示成“已复核”（§4.10）。

### 9.4 兼容性

- VS Code 1.90.0 及以上。
- 0.1.1 → 0.2.0 升级时，今日页行为保持不变，**且计价语义无任何变更**（§4.5 已确认 0.1.1 的峰谷判定与官方口径一致，0.2.0 只是把节假日表从“仅 2026”扩展到多年份，2026 年的数据本身不变）。CHANGELOG 需说明“历史金额按当前价目与节假日表估算”。
- 现有设置项名称和默认值保持兼容；0.2.0 不新增计价相关设置项（`holidays` 已足够，调休上班日不参与计价，见 §4.5）。
- `holidays` 建议由 `window` 调整为 `machine`：它决定峰谷分桶口径，按窗口配置会让同一台机器上的多个窗口得出不同分桶。注意 `machine` 作用域下**工作区级设置不再生效**，须写在用户设置中，CHANGELOG 与 README 需说明这一变更。若保持 `window` 作用域也可接受（`bucketSignature` 能保证不双计），代价是两个窗口会交替重写同一天的分桶、金额来回变化。
- 发布包继续支持 Windows/Ubuntu/macOS，不引入原生依赖。

### 9.5 可维护性

- 不引入新的运行时依赖；图表使用零依赖 SVG 或 Canvas。
- 历史聚合、周期计算、账本读写应有独立模块和单元测试。建议新增：`src/aggregate.js`（日聚合与 dayAgg 增量维护）、`src/history.js`（范围/粒度/周期键、查询聚合）、`src/ledger.js`（schema、max 合并、签名、原子写入、恢复）。
- 现有 `buildSnapshot` 的“只取今天”过滤逻辑需拆出，否则日聚合无处安放；拆分后今日页路径必须保持 0.1.1 的输出结构不变。
- 诊断输出包含账本状态，便于用户反馈问题。
- CHANGELOG、MARKETPLACE、README 同步更新。

### 9.6 体积

- VSIX 体积增长建议控制在 100 KB 以内（不含可能的图表代码）。
- 账本文件每年增长预计在几百 KB 量级；不设置强制上限。

## 10. 测试与验收

### 10.1 测试类型

**单元测试**

- 日/周/月/季/年周期键计算，含跨年周、闰年、月末、季末。
- 北京时间日界（UTC 16:00 切换）。
- 高峰/低谷边界：UTC 01:00 / 04:00 / 06:00 / 10:00 对应北京时间 09:00 / 12:00 / 14:00 / 18:00 的开闭区间（左闭右开）。
- **周末全天低谷，含调休上班的周六/周日**：固定用例 2026-02-14、2026-02-28、2026-10-10（均为补班周六），断言 `isPeak === false`。
- **落在工作日的法定假日为低谷**：固定用例 2026-02-16（周一，春节假期内），断言 `isPeak === false`。
- 范围边界落在周期中间时的“不完整周期”标记与环比基线规则。
- 同一 `message.id` 去重、流式快照取最大输出。
- 主请求/子代理分桶。
- 模型前缀过滤、未知模型回退。
- 币种切换、价目覆盖、节假日修改（含“改表后日志仍在的日期被重算”）。
- 账本 max 合并：幂等（同一输入连写 20 次结果不变）、单调（输入变小结果不变）、日志删除后不倒退。
- `bucketSignature` 不一致时的整日替换，以及“同一批请求不会同时进高峰和低谷桶”（总 token 不膨胀）。
- 账本损坏恢复、更高 schemaVersion 的只读降级、原子写入重试失败后的旧账本完好。
- schema 版本迁移。
- 多窗口并发写入（可用多进程或模拟 LWW 的并发写测试）。
- `lastRecomputedAt`：日志存在的日期刷新后更新时间；日志删除后不再更新；与 `bucketingStale` 互不影响。
- “无数据”与“零消费”的判定：无记录日期返回空态而非 0；全缓存命中日期返回 0 金额。
- FR-19 的只读探测：`settings.json` 缺失/非法/无权限三种情况下均不抛错、不创建文件（可用临时 HOME 断言文件未生成）。

**场景测试**

- 多日 fixture：跨日、跨周、跨月、跨季、跨年。
- 同一天多个模型、主/子代理混合。
- 非 DeepSeek 模型、`<synthetic>` 消息。
- 日志文件截断、追加、删除。
- **模拟 Claude Code 30 天清理**：删除超过保留期的日志目录后重新激活，验证已入账日期数值不变、未入账日期显示“无数据”而非 `¥0.00`、诊断中“最早可回溯日期”正确。
- **删除今天的日志**：今日页、状态栏、历史页“今天”三者金额仍相等且不下降，提示条出现，“按会话”分区给出明细可能小于合计的说明。
- 账本存在但日志不存在。
- 账本损坏、权限错误、`schemaVersion` 高于当前版本。
- 节假日与其前后补班周末相邻的区间（如 2026 春节：2/14 补班周六 + 2/15–2/23 放假 + 2/28 补班周六）。
- 冷启动：有账本 / 无账本 / 账本损坏三种情形，配合大日志目录验证首屏不阻塞。

**集成测试**

- 激活扩展后打开今日页，数值与 0.1.1 一致。
- 切换今日/历史标签页。
- 切换范围、粒度、币种、子代理、模型前缀。
- 状态栏保持今日口径。
- 空状态、错误状态。
- 诊断输出包含账本信息。

**跨平台**

- CI 矩阵：Windows、Ubuntu 22.04、Ubuntu 24.04。
- 三平台执行 `scenario_check` 和历史测试。
- Windows/Ubuntu 各安装一次 VSIX，验证侧边栏可打开。

## 12. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| Claude Code JSONL 格式变化 | 账本无法识别新记录 | 解析层容错；诊断输出坏行统计；必要时发布适配版本 |
| 内置节假日表不全或过期 | 历史金额偏高（落在工作日的法定假日被算成高峰） | 采用 holiday-cn 数据内置 2024–2027（§8.6）；`npm run sync:holidays` 年度更新；缺失年份显式提示，不静默计算 |
| 历史价目不准确 | 历史金额偏差 | 明确“估算”边界；提供 `rateOverrides`；README 说明金额会随版本变化 |
| 多窗口并发写入 | 账本损坏/重复计数 | 全量重算 + 原子替换 + 后写者胜；`bucketSignature` 防双计；不引入锁文件（§6.6） |
| 两个窗口 `projectsPath` 不同 | 同一天合计被低估（取大不叠加） | 已知限制写入文档；提供“重建账本”命令 |
| 账本只增不减 | 错误估算无法自助纠正 | FR-16 提供“从日志重建账本”，P1 必做 |
| 大量日志/长期历史 | 启动扫描和 UI 卡顿 | 冷启动读账本秒开、`dayAgg` 增量累加、无变化不写盘、性能测试 |
| 账本 schema 升级 | 旧版本不兼容 | `schemaVersion`、迁移函数、备份与重建、高版本只读降级 |
| 用户清理日志（手工 `claude purge`/手删） | 已记账日期不受影响；未记账日期永久缺失 | 账本持久化 + 逐桶 max；删除后金额不倒退；峰谷口径标 `bucketingStale`；无数据与零消费分开显示（§4.10） |
| **Claude Code 默认 30 天自动清理日志**（`cleanupPeriodDays`，静默） | 回溯上限只有约 30 天；扩展未运行期间的数据一旦过期即永久缺失 | 首次运行与诊断明确告知窗口上限（FR-19）；账本把保留期延长到“装了插件就在”；README 给调大 `cleanupPeriodDays` 的建议；不修改用户配置 |
| 用户以为“空白天 = 没花钱” | 误读为消费为 0，结论错误 | 空态与 `¥0.00` 视觉区分；诊断显示“最早可回溯日期”（FR-12、FR-19） |
| 侧边栏空间有限 | 图表/表格拥挤 | 响应式布局、折叠、横向滚动、明细表兜底 |
| Marketplace 审核 | 上架延迟 | 不联网、无遥测、README/隐私说明清晰 |

- 开发/打包：Node.js 22+、`@vscode/vsce`。

### 16.2 接线时序（顺序即正确性）

```text
扫描 → buildSnapshot（今日实时值）
     → syncLedger（聚合 → mergeDays → 必要时原子写盘）
     → applyTodayFloor（用「已更新的账本今日」与实时值逐桶取大）
     → publish
```

**这个顺序不能反**：若先兜底再写账本，本次刷新中"日志里已有、账本里还没有"的记录会被账本旧值覆盖掉一半，导致今日金额短暂变小。

写盘失败的整条路径都被 `try/catch` 包住，只记日志不抛异常——账本是派生数据，写不进去不能让今日页陪葬。

### 16.3 今日页语义变更与验证

今日页合计与按模型改为 `summarizeDay(max(实时, 账本今日))`。用本机真实日志对照 0.1.1 原算法（`buildSnapshot` 逐条 `requestCost` 累加）：

| 口径 | 0.1.1 | M2 | 差值 |
|---|---|---|---|
| CNY | 2.3441204000000013 | 2.3441204 | 1.3e-15 |
| USD | 0.35161806 | 0.35161806 | 5.6e-17 |
| 关闭子代理 | 2.34412040 | 2.34412040 | 1.3e-15 |
| 请求数 / token | 138 / 18123665 | 138 / 18123665 | 0 |

差值来自浮点累加顺序（逐条累加 vs 按桶相加），量级 1e-15，不影响展示精度。**FR-04「今日页与 0.1.1 一致」成立**；自检里还加了一条更硬的验收：今日页金额 === 历史页「今天」金额，逐位相等。

### 16.5 与文档的差异

1. **`daysWithData` 与「有消费的天数」不等价**。账本保存所有模型，某天可能只有未计入 `modelPrefixes` 的请求。实测近 30 天里 22 天有账本记录，但按 `deepseek` 口径只有 1 天有金额。已加「无计入消费」标记与说明，避免用户误判为数据丢失。
2. **历史页的空态与错误态合并处理**：`reason === 'unavailable' | 'error'` 时清空并显示原因，不使用 `empty` 字段区分（`empty` 只表示"范围内有账本但无计入消费"）。
